## 8주차 회고

이번 주는 서울로 AI 에이전트를 코스 생성에 특화되도록 구조를 바꾸었다. 기능을 덜어내면서 여행 계획 생성 에이전트로서의 역할을 다시 설정하였다.

## 초기구조의 문제점

처음 구조는 장소 추천, 장소 소개, 코스 생성이 각각 별도의 기능 모듈로 흩어져 있었고, 진입점도 기능마다 따로 있었다. LLM이 사용자 입력에 따라 모든 호출을 하다보니 서버가 하는 일이 넓게 퍼져 있다 보니 어떤 요청이 어디로 흘러가는지 한눈에 들어오지 않았고, 같은 성격의 로직(장소를 고르고 설명을 붙이는 일)이 중복 되었다.

## 해결방법

### 경로 생성 로직은 클라이언트에 위임하였다

가장 크게 바꾼 건 방문 순서를 최적화하던 경로 생성 로직을 서버에서 통째로 들어낸 것이다. 코드를 설계할때 서울로의 코드를 참고하여 만들다 보니 라우팅 경로 생성까지 lewisai파일 에서 동작하도록 코드가 작성되어 있었고 실제 지도에 오버레이되는 폴리라인 생성 로직은 이미 프론트에서 좌표를 받으면 자동으로 경로를 생성하도록 설계되어 있다. 같은 일을 양쪽이 하는 점을 수정하였고 경로·거리 계산은 프론트가, AI 서버는 장소와 좌표와 선정 이유만 넘기는 역할을 분기했다. 서버에서 상당한 분량의 코드를 삭제했고, 거리 계산은 라우팅용이 아니라 주변 검색의 반경 필터와 혼잡도 지점 매칭에만 쓰이는 최소한의 유틸리티만 남기도록 했다.

### AI의 역할을 장소선택 + 장소 선택이유로 출력되게하였다

AI가 해야 할 일을 더 명확하게 정의하였다 이전에는 AI가 장소 이름만 랜덤하게 골라주는 수준이었는데, 이젠 이사람의 요청에 따라 왜 이 장소인지(선정 이유) 와 거기서 무엇을 할 수 있는지(행동추천)을 함께 만들어내도록 코스 생성 단계를 다시 설계했다. 이때 오늘 날짜, 시간대, 동반 유형, 나이대, 목적 같은 맥락과 실시간 혼잡도를 프롬프트에 함께 넣어서, 지금 실시간 서울을 기준으로 이유를 쓰게 만들었다. 

### 하나의 그래프로 흐름을 통합했다

하나의 상태 기반 파이프라인으로 합쳤다. 요청이 들어오면 먼저 의도를 판별하고, 코스 요청이면 후보 검색 → 장소 선정 → 혼잡도 확인 → 주변 정보 조회 → 서사 작성이라는 단계를 거치고, 코스가 아니면 잡담으로 빠지도록 분기를 딱 둘로 설계했다. 사용자가 경로 생성 칩을 선택해서 들어오면 의도가 이미 정해진 것이니 라우터를 건너뛰고 코스 생성 파이프라인으로 바로 처리하고, 자연어로만 들어오면 라우터가 코스인지 잡담인지 판별하게 했다. 

### 장소 생성 과정을 챗봇에서 보이도록 하였다

결과만 던지지 말고 어떻게 이 장소들이 나왔는지 과정을 보고 싶었다. 그래서 각 단계(후보 검색, AI 선정, 혼잡도 확인, 주변 정보, 서사 작성)를 응답에 함께 실어 보내고, 특히 장소 선정 단계에는 장소별 선정 이유까지 담아서 사용자가 왜 이렇게 짜였는지 설계하였다. 이 조회는 지금 테스트 단계에서만 나오는 부분이고 실제 클라이언트에선 바로 코스가 생성되도록(원래 로직대로)할 것이다.

### Visit Seoul API는 주변 정보(식당 우선)로 범위 축소

외부 관광 API도 역할을 다시 정의했다. 원래는 VisitSeoul API로 장소 자체를 찾으려 했는데 장소에 대한 정보는 RAG 데이터에서 사용해야 할루시네이션이 없을것 같고, 이 방식이 RAG를 쓰는 이유인것 같아 외부 API는 이미 확정된 장소에서 주변 음식점과 문화행사 정보를 채우는 용도로만 쓰도록 바꿨다. 하지만 해당 API의 스키마가 현재 사용중인 구조와 맞지않아 호출에 장애가 생겼고 사실 문화행사 데이터와 관광지 정보 데이터는 strangemap에 이미 구현되어 있어서 맛집 정보에 대한 API만 받도록 다시 수정하였다.

### LLM은 폴백 구조로 호출 제한 안정성 확보

모델 호출은 한 곳에 의존하지 않도록 폴백 구조로 감쌌다. 기본은 제미나이를 우선 쓰되, 할당량 초과 카테부에서 받은 클로드api키가 사용되도록 하였다

### 장소 생성에 필요한 데이터 임베딩
기존에 RAG로 출력 할 수 있는 장소수는 4가지의 권역(강남, 강북, 강동, 강서)로 나뉘어있고 권역 크기가 넓다보니 해당 장소 생성간 거리가 10km 이상인 코스가 생성되었고 이는 실제 프로덕션으로 사용하기엔 불가했다. 이를 해결하기 위해 strangemap에서 사용하고있는 장소 정보 데이터를 모두 json 포맷으로 작성하여 198가지의 데이터를 만들었고 임베딩하였다. 장소수를 추가하여 권역별로 이태원/한남, 성수/건대 등으로 세세하게 나눠도 최소 10곳의 장소를 클러스터링 할수 있게 되었다.
