> 목표는 **응답 품질(0순위)**이다. 레이턴시(1순위, 병렬화)는 이 설계가 확정된 뒤에 착수한다 —
> 데이터·노드가 바뀌면 측정 기준선이 흔들리기 때문.
>
> 이 문서의 모든 수치는 2026-07-28 실측한값을 문서로 나타낸 것이다 (추정 아님). 측정 방법은 각 항목에 적어 둔다.

## 0. 무엇을 왜 바꾸는가

현행 파이프라인에서 실측으로 확인된 문제 네 가지:

| 문제 | 실측 |
|---|---|
| 핫플레이스가 개별 편집숍으로 채워짐 | 핫플 307곳 중 **244곳**이 `visitseoul_shopping` 개별 매장 |
| 맛집 탐방 목적이 빈약하고 오분류 | 73곳(전체의 9%), 그중 **17곳**이 갤러리·방송국 사옥 |
| 카테고리별 체류시간이 사실상 미작동 | 매핑 적중 164곳(**20%**), 나머지 652곳은 전부 기본 60분 |
| 끼니가 자동 삽입이라 통제 불가 | 오후 창(12~18시)은 **시작하자마자 점심**, 당일치기는 2시간 40분 공백 뒤 저녁 억지 삽입 |

핵심 전환은 **식사를 "자동 삽입되는 부산물"에서 "사용자가 고르는 축"으로 승격**하는 것이다.
그 결과로 목적 칩에서 "맛집 탐방"이 빠지고, 밀캐시 1,234곳이 코스 다양성의 실질적 원천이 된다.

## 1. 칩 단계 구성

현행 8단계 → **9단계**. 목적에서 "맛집 탐방"이 빠지고 "식사" 단계가 신설된다.

```
① audience    현지인 / 관광객
② [분기]      현지인 → window(시간 범위)  |  관광객 → days(1~6일)
③ meals ★신설  아침 10:00 / 점심 13:00 / 저녁 19:00   (다중, 0개 허용)
④ companion   혼자·친구와·연인과·배우자와·아이와·부모님과 (다중)
⑤ purpose     자연·힐링 / 문화·예술 / 관광 명소 / 체험·놀거리 / 데이트 / 핫플레이스 / 쇼핑  ← 7칩
⑥ location    9권역 + 상관없음 (관광객은 days만큼 다중)
⑦ congestion  여유 / 보통 / 상관없음
⑧ pace        알찬(5곳) / 여유로운(3곳)
⑨ confirm
```

### 왜 ③이 시간 단계 바로 뒤인가

현지인은 ②에서 시간창을 정하므로, 그 창에 어떤 끼니가 들어가는지 즉시 판단해 칩에 표시할 수 있다.
**식사 시각이 고정(10/13/19시)이라는 것을 고르는 시점에 알려준다.**

```
   ┌──────────────┬──────────────┬──────────────┐
   │  아침 10:00  │  점심 13:00  │  저녁 19:00  │
   └──────────────┴──────────────┴──────────────┘
   고른 끼니만 코스에 들어가요. 시각은 고정이에요.
```

### 고정 시각의 타당성 (실측)

밀캐시 1,234곳의 `use_time`을 파싱해 각 시각에 영업 중인 곳을 셌다.

| 끼니 | 영업 중 |
|---|---|
| 아침 10:00 | 367곳 |
| 점심 13:00 | 1,075곳 |
| 저녁 19:00 | 997곳 |

> **[정정] `app/core/scheduler.py` 의 "아침 영업 식당이 사실상 없다" 주석은 틀렸다.**
> 그 근거는 *한식당 18곳 표본*이었다. 전체 1,234곳 기준 09시 이전 개점이 124곳(10.3%),
> 10시까지 누적 367곳이다. 내용도 아침에 맞다 — 한남북엇국·설담재설렁탕·금수복국·
> 제주미향해장(24시간) + 07:30 개점 브런치 카페 다수.
> 권역별로는 잠실·송파(2곳)·관악·사당(3곳)만 얇고 나머지 6개 권역은 9~45곳으로 충분하다.

### 결정 필요 — 끼니 선택이 시간창을 확장하는가

현지인이 "오후(12~18시)"를 고르면 아침 10시·저녁 19시가 창 밖이다.

- **A. 창 밖 끼니 비활성화** — 정직하지만 "오후 코스인데 저녁은 먹고 싶다"를 막는다

B가 사용자 의도에 맞는다. "저녁 먹고 싶다" = "저녁까지 있겠다".

## 2. 데이터 변경

### 2-0. 먼저 — 무엇이 검색을 결정하는가

재태깅 설계의 전제. **`category` 도 `coarse_category` 도 검색에 관여하지 않는다.**

| 필드 | 역할 | 검색 필터 |
|---|---|---|
| **`purpose_tags`** | 목적 칩 7종 매칭 (`pt_<slug>` 불리언 메타로 전개) | ✅ **하드 필터** |
| **`area`** | 권역 칩 매칭 | ✅ 하드 필터 |
| `coarse_category` | LLM 다양성 규칙용 표시 | ❌ |
| `category` | 프롬프트 표시 + dwell 폴백 | ❌ |

`_search_pool()` 이 만드는 실제 Chroma `where` (실측 덤프):

```json
{"doc_type":"place", "area":"종로·중구",
 "$or":[{"pt_culture":{"$eq":true}}, {"pt_food":{"$eq":true}}]}
```

장소 선정 워크플로우:

```
목적 7칩 ─┬─→ purpose_slugs() → pt_* 하드 필터  ┐
          └─→ PURPOSE_RULES[].query 확장어 ────┤
권역 칩 ────→ area 하드 필터                    ├→ Chroma 검색 (40건)
자유입력 ───→ 임베딩 쿼리에 이어붙임             ┘
                          ↓
        _geo_rerank (앵커 반경 + 거리·유사도 블렌드) → 후보 10~15곳
                          ↓
    LLM 프롬프트 한 줄:  "- 서순라길 (자연 · 도시공원 · 상시개방 · 0.6km): 본문…"
                                       ↑        ↑
                                    coarse   category   ← 여기서 처음 등장. 표시 전용
                          ↓
        LLM 이 후보 중 N곳 선택 + reason + activities
        (coarse 는 "같은 대분류 연속 3곳 금지" 판단에만 사용)
```

- **후보에 오르는가** = `purpose_tags` + `area`
- **어떤 순서로 오르는가** = 임베딩 유사도 + 지리 거리
- **무엇을 고르는가** = LLM
- `coarse`/`category` = LLM 이 보는 라벨. 후보 진입 여부와 무관

### 2-1-1. `coarse_category` 와 `category` 의 존치 여부

**`coarse_category` — 유지.** 다양성 규칙(`_SELECT_PROMPT` 의 "같은 대분류 연달아 3곳 금지")의
축으로 실제 기능한다. `category`(27종)는 너무 잘게 나뉘어 이 판단에 못 쓴다 —
박물관·미술관/화랑·기타전시시설·공연시설은 전부 다른 category 지만 사용자에겐 다 같은 "문화"라,
category 기준으로 연속 금지를 걸면 박물관→미술관→전시시설이 통과해 버린다.
문화가 194곳으로 최대라 이 위험이 실재한다.

**`category` — 이번 라운드는 그대로 두고, 다음 라운드 정리 대상.**
현재 이 필드는 통일된 분류 체계가 아니라 **4개 출처의 원본 라벨을 그대로 담은 필드**다:

```
visitseoul_culture   박물관, 미술관/화랑, 도시공원, 기타문화관광지, 기타전시시설, 랜드마크관광…
visitseoul_history   역사관광
visitseoul_nature    자연관광
visitseoul_shopping  쇼핑
seoul_places         상권·역세권, 공원·자연, 한강·다리, 고궁·역사, 전망대·산, 야경·전망…
```

그래서 같은 것을 가리키는 라벨이 중복된다 —
자연: `자연관광`(53)·`도시공원`(47)·`공원·자연`(15)·`공원·정원`(8) /
문화: `박물관`(51)·`미술관/화랑`(50)·`미술관·박물관`(1).

**이것이 `DWELL_MIN` 이 20%만 적중한 원인이다** — 매핑 키를 `seoul_places` 어휘로만 짜서
`visitseoul` 어휘가 전부 미스났다. LLM dwell 도입 후 `category` 의 기능적 역할은
프롬프트 표시만 남으므로, 27종 → 12종 재작성은 다음 라운드로 미룬다.
이번 라운드에 얹으면 변경 폭이 커져 무엇이 품질을 올렸는지 분리되지 않는다.

### 2-1-2. 목적 태그 기준표 — 전체 카테고리

**원칙: 고정된 장소는 목적에 따라 행동이 바뀌므로 여러 역할에 중복 소속될 수 있다.**
쇼핑과 식사만 분리한 이유는 그 둘이 **단일 역할에 국한**되기 때문이다.

#### 적용 방식 — 덮어쓰기가 아니라 **합집합(최소 보장)**

카테고리 규칙은 기존 장소별 태그를 **더한다**. 덮어쓰면 안 된다 —
`뚝섬 한강공원 수영장` 이 `레저스포츠시설` 이라는 이유로 자연·힐링을 잃는다.

## 3. 노드 구조

식사 시각이 칩만으로 확정되므로 **시간 골격을 장소 선정보다 먼저 만들 수 있다.**
이것이 응답 품질에 가장 크게 기여하는 구조 변화다.

```
현행
START → router → parse_intent → retrieve → select_places → nearby → schedule → enrich → compose → END

변경
START → plan → retrieve → select_places → fit_schedule → meals → enrich → compose → END
         ↑                      ↑              ↑           ↑                    ↑
      시간 골격            장소+이유+행동     세그먼트     끼니 후보         ↘ events (병렬)
      (칩만, 0ms)        +체류시간 희망치      배분      (선택한 끼니만)
```

### 3-1. `plan` (신설) — 순수 계산, 0ms

칩만으로 하루의 뼈대를 만든다.

```
창 09~21시, 끼니 [점심, 저녁] 선택 시

  09:00 ─────── 13:00 ─── 14:00 ─────── 19:00 ─── 20:00 ─── 21:00
  │  세그먼트 A  │  점심   │  세그먼트 B  │  저녁   │ 세그먼트 C │
  │   (4시간)    │  고정   │   (5시간)    │  고정   │  (1시간)  │
```

이 골격이 `select_places` 프롬프트로 들어가서 LLM 이:

- 각 세그먼트에 몇 곳이 들어갈지 알고 장소를 고른다
- **"점심 13시 직후 첫 장소"** 라는 맥락을 알고 activities 를 쓴다
- 체류시간 희망치를 세그먼트 길이에 맞춰 제안한다

### 3-2. 식사 미선택 시 — **노드 구조를 갈라서는 안 된다**

세 경우가 전부 `plan` 의 **출력 데이터 차이**로 흡수된다.

| 경우 | plan 출력 | 하위 노드 |
|---|---|---|
| 창 + 끼니 선택 | 세그먼트 N개 + 식사 앵커 N개 | 동일 코드 |
| 창 + 끼니 없음 | 세그먼트 **1개**, 앵커 0개 | 동일 코드 |
| 창 없음 (자연어 경로) | 빈 골격 | 시간표 생략 (현행 유지) |

조건부 엣지로 분기하지 않는 이유:

1. `fit_schedule` 은 "세그먼트 리스트에 장소를 배분"하는 로직이라 **세그먼트가 1개든 3개든 같은 코드**다.
   분기하면 같은 로직이 두 벌로 갈라진다.
2. `meals` 노드는 밀캐시 **파일 읽기**라 0ms다. 스킵해서 얻는 게 없다.
3. 경로가 갈리면 두 경로의 `stops[]` 출력 계약이 어긋날 위험이 생긴다.
   클라이언트가 이 스키마를 그대로 쓰므로 피해야 한다.
4. 테스트 조합이 배가된다.

> **단, `plan` 함수 내부에서는 명시적으로 갈라야 한다** — 끼니 0개일 때 세그먼트를
> 창 전체로 만드는 분기는 필요하다. 그래프 레벨이 아니라 함수 레벨 분기다.

### 3-3. `schedule` → `fit_schedule`

현행은 **그리디 앞채움**이다 — 고정 체류시간을 앞에서부터 채우다 넘치면 버린다.
그 결과(실측):

```
4곳 요청 → 3곳만 앉고 1곳 flex, 창 50분 유휴
당일치기 3곳 → 14:50 종료, 2시간 40분 공백 뒤 저녁 억지 삽입
2일 packed → 1일차 17:34 종료, 21시까지 146분 유휴
```

식사가 고정 앵커가 되면 **세그먼트별 예산 배분**으로 바뀐다.

```
세그먼트 B (14:00~19:00, 300분), 장소 2곳 배정
  → 이동 추정 40분 제외 = 260분 예산
  → LLM 희망치 [90, 120] → 비율대로 신축 → [108, 152]
  → 넘치면 하한(30분)까지 축소, 남으면 분배
```

`place_count` 칩이 지켜지고, 유휴 시간이 사라지고, "90분 아니면 30분" 이분법이 없어진다.

### 3-4. `nearby` 분해

| 현행 | 변경 | 이유 |
|---|---|---|
| 식당 풀 | → `meals` 노드 | 선택한 끼니에만 필요. 파일 읽기라 ~0ms |
| 실시간 행사 | → `compose` 와 병렬 | 최종 payload 에만 쓰여 크리티컬 패스에 있을 이유 없음 (-1.4s) |

### 3-5. `router` / `chitchat` 제거

칩 경로에서 이미 무동작이다 (`intent`·`req` 가 주입돼 있어 즉시 리턴 — 프로파일에서
LLM 호출이 select·compose 2회뿐인 것이 증거). **레이턴시 이득은 0이고 순수하게 구조가 단순해진다.**

주의: `/agent/chitchat` 은 `app/api/routes/chitchat.py` 에 **별도 라우트로 살아 있다.**
그래프에서 빼는 것과 라우트를 지우는 것은 별개 결정이다.

`parse_intent` 는 자연어 입력 처리를 위해 `refine` 형태로 `plan` 앞에 남긴다 — 별도 과제(6장).

## 4. 체류시간 · 식사 선정 규칙

### 4-1. 체류시간은 LLM 이 산출, 카테고리 매핑은 폴백 전용

현행 `DWELL_MIN` 은 **80%가 미작동**이다 (실측).

```
매핑 적중  164곳 (20%)
기본값 폴백 652곳 (80%) ← 전부 60분
```

`DWELL_MIN` 의 키가 `seoul_places` 계열 카테고리만 커버해서, 가장 많은
쇼핑 225 · 역사관광 77 · 박물관 51 · 미술관/화랑 50 · 도시공원 47이 전부 기본 60분이었다.
**국립중앙박물관도 60분, 동네 편집숍도 60분.**

```
LLM 프롬프트  → DWELL_MIN 미노출. activities 근거로 dwell_min 자유 산출
서버 처리     → 값 있으면 15~180분 클램프 후 사용
             → 없거나 파싱 실패 → DWELL_MIN 카테고리 매핑
             → 그것도 미스 → 60분
```

**낡은 매핑을 프롬프트에 넣으면 LLM 을 잘못된 기준에 앵커링시킨다.** 안전망으로만 둔다.

비용은 0에 가깝다 — `select` 가 이미 `activities` 를 만드니 같은 JSON 에 `dwell_min` 한 필드를
추가하는 것이고, 스톱당 10자 남짓이라 생성 시간 증가는 무시할 수준이다.
`select → fit_schedule` 순서라 순환 의존도 없다.

### 4-2. 식사 후 activities 는 LLM 판단

`plan` 이 만든 골격(식사 시각 포함)이 `select` 프롬프트에 들어가므로,
LLM 이 "점심 13시 직후" 라는 맥락을 알고 그에 맞는 행동을 제안한다.

### 4-3. 밀캐시 — 임베딩 불필요, 순수 랜덤도 안 됨

**임베딩하지 않는다.** 필터 축(종류·거리·영업시간)이 전부 메타데이터고,
의미 검색이 필요한 시점은 "매운 거 먹고 싶어" 같은 자연어가 들어올 때뿐이다(향후 과제).
1,234곳 임베딩 비용·색인·검색 지연을 지금 낼 이유가 없다.

**권역별 순수 랜덤은 위험하다.** 권역이 너무 넓다 (실측: 중심~최원거리).

| 권역 | 최원거리 | 평균 |
|---|---|---|
| 홍대·마포 | **11.0km** | 2.0km |
| 강북·성북 | 9.2km | 3.8km |
| 성수·건대 | 8.7km | 1.6km |
| 종로·중구 | 4.0km | 1.2km |

홍대에서 점심인데 랜덤으로 은평구 식당이 나올 수 있다.

**권장: 반경 제약 + 그 안에서 가중 랜덤.** 임의 장소 120곳 기준 재고 실측:

| 끼니 | 1.5km 안(중앙값) | 3km 안 | 1.5km에 3곳 미만 |
|---|---|---|---|
| 아침 10시 | 8곳 | 28곳 | **26%** |
| 점심 13시 | 28곳 | 86곳 | 13% |
| 저녁 19시 | 28곳 | 80곳 | 16% |

점심·저녁은 1.5km 안에 중앙값 28곳이라 랜덤 뽑기에 충분하다. **아침만 얇아 3km 폴백이 필요하다.**

현행 `_meal_options()` 의 "앵커 1.5km 안 거리순 상위 3곳"은 같은 권역·같은 앵커면
**결정적으로 같은 답**이 나온다 — "항상 같은 식당만 나온다"는 체감의 원인이다. 바꿀 축:

- 거리순 단독 → **거리 + 종류 믹스 + 동반/목적 적합도** 블렌드 후 가중 랜덤
- 반경을 끼니별로 다르게 (저녁은 넓혀도 이동이 자연스럽다)
- 같은 권역 반복 요청 시 **회전** — 앵커가 같아도 매번 다른 상위권이 나오게

4. **핫플레이스 커버리지** — 8개 권역이 12곳 미만. 태그로는 안 풀린다.
   권역별 핫플 거리 데이터 보강 또는 핫플 칩 전용 필터 완화 예외. **미결.**

6. **K-콘텐츠 31곳 category 개별 매핑** — 방향은 확정, 31곳 실제 값 할당 남음.
7. `category` 27종 → 12종 재작성 — 다음 라운드 (2-1-1절).
3. **자연어 입력(note) 선반영** — 별도 과제. 실측된 문제:
   - 위치 의도가 무시된다 ("강남 쪽으로" 해도 `area` 필터가 칩 값으로 하드 고정, 상위5 겹침 40%)
   - 부정이 정반대로 작동한다 ("박물관은 빼줘" → 쿼리에 "박물관"이 두 번 들어가 유사도 상승,
     실제로 서울공예박물관이 신규 진입)
   - 칩 경로는 `parse_intent` 를 건너뛰므로 구조화 추출이 아예 없다
   → `refine` 노드로 note → 칩 보정. note 가 비면 스킵(0ms), 지명은 룰베이스로 선처리.
4. **특정 식당 지정** — 자연어로만 받는다. 코스 생성을 쓰는 사용자는 명확히 가고 싶은 식당이
   없다는 것이 제품 전제.
5. **레이턴시 병렬화** — 이 설계 확정 후 착수. 측정된 기준선은 `docs/` 외부 참조:
   3일 코스 38.5s (compose 23.1s / select 10.6s / 나머지 4.8s), LLM 이 87%.
   일자별 병렬화로 ~15s 예상.
