## 9주차 회고

8주차([remind_week08.md](remind_week08.md))에서 코스 생성 전용 에이전트로 구조를 재설계했다면, 9주차는 기능을 더 고도화 했다. 하나는 사용자 입력(칩) 구조와 개인화 로직을 다시 설계한 것이고, 다른 하나는 정적인 주변 정보를 미리 캐싱해서 요청당 발생하던 레이턴시를 없앤 것이다.

## 문제점

1. 8주차까지는 칩이 단일 선택이었다. 목적·동반·위치를 각각 하나씩만 고를 수 있다 보니 사용자가 실제로 원하는 조합("친구랑 맛집 탐방도 하고 사진도 찍고 싶어" 같은)을 표현할 방법이 없었고, 개인화도 나이대 태깅을 기준으로 장소를 분기하는 방식이었는데 실제로 테스트해보니 나이대만으로는 같은 장소를 골라도 왜 그 장소인지, 거기서 뭘 하면 좋은지가 불분명 하다.

2. 코스에 들어가는 식당 정보를 요청마다 Visit Seoul 상세 API를 실시간으로 호출하다 보니 rate limit 때문에  코스에서는 조회만 20~30초나 걸린다.

## 해결방법 및 결과

### 칩을 다중 선택으로 바꾸고 개인화 축을 나이에서 목적·동반으로 재설계했다

사용자 선택 필드를 동시에 선택할수 있게 바꾸었다. 목적을 여러 개 고르면 각 목적의 검색어·분위기 태그·선정 규칙을 합집합으로 묶어 하나의 조건으로 만들고(`purpose_rule()`), 동네를 여행 일수만큼 여러 개 고르면 그 순서대로 하루씩 배정되게(1일차 홍대·2일차 강남…) 했다. 원래는 나이대를 기준으로 해당 장소 선호도에 따라 추천 하려했으나 사람이 실제 어딘가를 갈때 "무엇이 누구를 왜 움직이는가"를 기준으로 다시 생각해 보았다. 목적은 검색(장소 선정) 자체를 움직이게 해서 목적 칩이 바뀌면 후보로 올라오는 장소 자체가 달라지도록 했고, 동반자는 검색에는 관여하지 않고 행동·서사만 바뀌도록 했다. 
임베딩 장소가 지역구 단위로 저장되다 보니(잠실, 뚝섬등) 같은 장소라도 누구와 어떤 목적으로 오느냐에 따라 할 일이 생성되는 일정도 다르게 하고 싶었다 (친구와 잠실이면 야구 관람, 가족+ 아이와 잠실이면 롯데월드). `select_places_node`에서 `companion_rule()`을 프롬프트에 주입해서 장소 후보는 그대로 두고 `activities`·`reason`만 달라지게 했다. 이 생성은 모두 LLM이 관여 하기 때문에 환각방지,더 다양한 행동 추천이 나올수 있도록 고도화 할 계획이다. 이 밖에도 사용하지 않는 연령 태깅이나 장소 분위기 태깅 로직들도 모두 정리했다.

### 식당 정보를 권역별로 미리 캐싱해서 레이턴시를 줄였다

레이턴시 개선을 위해 고민하다 식당은 한동안 바뀌지 않는 정적인 정보목록이기 때문에, 요청이 들어올 때마다 API를 부르는 대신 권역(9개) 단위로 미리 캐싱 해놓는 형태로 바꿨다. 오프라인 스크립트(`scripts/build_meal_cache.py`)가 "음식" 카테고리 전체(1249건)를 페이지네이션으로 훑고 각 장소의 좌표로 가장 가까운 권역에 배정해서 `data/meal_cache/`에 권역별 JSON으로 저장해두면, 런타임(`app/tools/meal_cache.py`)은 파일을 읽고 반경으로 필터링만 하면 되기 때문에 API 호출없이 사용가능하다. 처음에는 권역 좌표를 중심으로 키워드 검색 + 반경 필터로 캐시를 만들어 키워드 검색이 제목·요약 문자열 매칭이라 서울 전체에서 96곳밖에 못 잡았고, 그래서 visitseoul의 API 스키마에 내가 받아야 하는 정보만 나오도록  "음식" 카테고리의 모든 정보를 특정 스키마(이름, 좌표, 설명)만 가져오고 좌표 기준으로 권역을 배정하는 방식으로 바꾸니 1249곳 모두 json포맷으로 저장되었다. 실제 코스 요청으로 확인해보니(종로·맛집 탐방) 점심 슬롯 3곳이 인사동 앵커 기준 0.02~0.04km 이내에서 라이브 호출 없이 캐시만으로 정확히 배분됐다. 다만 관악·사당처럼 Visit Seoul 원본 데이터 자체가 적은 권역은 캐시 풀이 얇아서 기존처럼 직접 탐색 하라는 폴백 멘트가 나오도록 하였다.
