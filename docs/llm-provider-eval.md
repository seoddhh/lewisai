## 1. 무엇을 비교하는가 — arm 정의

arm = 비교하려고 나눠놓은 조건. 여기서는 **챗 LLM 프로바이더만** 바꾼다.

| arm | 모델 | 쿼터 | 비고 |
|---|---|---|---|
| **A** | `solar-open2` | 400 RPM / 150k TPM | 현행 기본값 |
| **B** | `gemini-3.1-flash-lite` | **15 RPM** / 일 500회 | 실험 전체의 병목 (→ 4절) |
| **C** | `claude-haiku-4-5` | 계정 티어에 따름 | 입력 $1 / 출력 $5 per MTok |

**고정하는 것** — 하나라도 같이 움직이면 원인 분리가 안 된다.

```
컬렉션          seoulro_v2 (1651건)      ← 3 arm 공통
임베딩          ollama / qwen3-8b        ← 챗과 독립. arm 간 후보 목록이 동일해야 한다
프롬프트        현행 원문 그대로          ← 모델별 튜닝 금지
페르소나·seed   고정 세트                 ← 2절
온도·max_tokens LLM_TEMPERATURE=0.7 / 4000
```

프롬프트를 모델별로 손보고 싶으면 별도 arm(A′ 등)으로 분리하고 표를 따로 낸다.
같은 표 안에서 섞으면 "모델이 좋은 건지 프롬프트를 더 만진 건지"를 말할 수 없다.

## 2. 평가 대상은 에이전트 하나가 아니라 4개 태스크

`get_llm()` 호출 지점이 성격이 완전히 다르다. 하나의 점수로 뭉개면 결론이 안 나온다.

| # | 태스크 | 위치 | 성격 | 채점 방식 |
|---|---|---|---|---|
| ① | 라우팅·칩 파싱 | `nodes/common.py:92` | 분류 + 구조화 추출 | **정답 라벨 → 정확도/F1** |
| ② | select (장소 선정) | `nodes/course.py:601` | 후보 내 제약 만족 선택 | **규칙 기반 (정답 불필요)** |
| ③ | compose 전역·일차 | `nodes/course.py:1052,1057` | 서술 생성 | 휴리스틱 + judge |
| ④ | compose 스톱 카드 | `nodes/course.py:1064` | 서술 생성 (3곳씩 청크) | 휴리스틱 + judge |

문서의 설득력은 **①②를 코드로 못 박고 ③④에만 judge 를 쓰는 분리**에서 나온다.
지난 A/B 에서 쓴 "LLM 판정 없이 코드로만 계산한다" 원칙을 그대로 이어간다.

### 데이터셋

- **코스 세트** — 페르소나 30개. 권역 9 × 목적 × 동반 × audience(로컬/여행자) × 1일/3일
  커버리지 매트릭스로 뽑는다. 기존 10개는 종로·홍대·강남에 몰려 있어 확장이 필요하다.
- **라우팅 세트** — 40~60문장. 코스 요청 / 잡담 / **경계 케이스**(장소 이름만 던지기,
  코스 요청처럼 보이는 질문)에 정답 라벨을 붙인다. 태스크 ① 전용이며, **유일하게
  정확도로 딱 떨어지는 표**가 나오는 구간이라 반드시 포함한다.
- **반복** — seed 3회(`chat.py` 의 `seed` 파라미터). 반복 표준편차를 같이 싣는다.
  **arm 간 차이가 반복 분산보다 작으면 결론은 "차이 없음"이다.**

## 3. 지표 — 4계층

### L0. 운영 (전부 코드, 판정 불필요)

- 폴백률 (`source == "mock"` 비율)
- JSON 파싱 실패율 — `_select_days` 의 `salvage_objects` 부분복구 발동 횟수
- **노드별 지연** — compose 는 `asyncio.gather` 라 **가장 느린 콜이 전체를 정한다.**
  평균이 아니라 max 를 기록할 것
- p50 / p95 end-to-end
- 입출력 토큰 → **코스 1건당 원가(₩)**
- 429 / 5xx 비율

### L1. 제약 준수 (코드, 정답 불필요 — 가장 강력한 증거)

- **후보 목록 밖 장소 환각률** — 화이트리스트 대조. **0이 아니면 그 arm 은 탈락 사유.**
  프로바이더 비교에서 가장 중요한 단일 지표로 본다
- 칩 준수율 — 요청 권역·목적 일치, `days` × 슬롯 규격, 하루 스톱 수
- 중복 장소 재등장, 필드 누락
- 200m내 스톱쌍 % (지리 응집), 대분류 1종 코스 % (다양성)
- 스케줄 정합성 위반 — 영업시간 밖 배치, 이동시간 초과 (`core/scheduler.py` 결과로 검증)

### L2. 검색–생성 정합 (RAG 특유)

- **groundedness** — 스톱 설명의 사실 주장이 해당 문서 `ragText` 에 근거하는가.
  근거 없는 주장 비율
- context utilization — 후보로 넘긴 정보 중 실제 서술에 반영된 비율

### L3. 서술 품질

- 광고성 수식 / 실용어 밀도 — 기존 `PUFF`/`PRACTICAL` 어휘 카운터 재사용.
  **코드로 되는 프록시라 judge 보다 신뢰도가 높다**
- pairwise 선호 (judge) — 실행 가능성 / 칩 반영도 / 한국어 자연스러움 3축
- 프롬프트 톤 규칙 위반 건수

### L4. 사람 스팟체크

블라인드로 20~30건 직접 라벨링한 뒤 **judge 와의 일치율(Cohen's κ)** 을 낸다.
LLM-judge 를 쓸 때의 핵심 규율이다 — **judge 를 믿기 전에 judge 를 먼저 평가하고
그 수치를 문서에 명시한다.** κ 가 낮은 축은 결론에서 제외한다.

## 4. 제미나이 15 RPM — 실험 설계를 지배하는 제약

### 콜 수 계산

`_STOPS_PER_CALL = 3` 기준, 코스 1건당 LLM 콜은:

```
1일 · 스톱 4곳 :  select 1 + compose(전역 1 + 일차 0 + 청크 2)          = 4콜
3일 · 스톱 12곳:  select 1 + compose(전역 1 + 일차 3 + 청크 2×3=6)      = 11콜
자유입력 경로   :  위 + parse_intent 1콜
```

페르소나 30 × seed 3 = **90회 실행 ≈ 450~600콜**.

### 15 RPM 에서 무슨 일이 벌어지나

1. **compose 는 `asyncio.gather` 로 3~10콜을 동시에 던진다.** 15 RPM 계정에서는
   코스 1건만으로도 순간 한도를 넘겨 429 가 난다. **그냥 돌리면 arm B 는 측정 자체가 실패한다.**
2. 500회/일 한도 대비 450~600콜은 **하루치를 통째로 소진**한다. 재실행 여유가 없다.

### 대응 (이 순서로 적용)

1. **평가 하네스에서만 동시성 제한** — `asyncio.Semaphore(1)` 로 arm B 의 LLM 콜을 직렬화하고
   콜 간 최소 4초 간격을 강제한다. 앱 코드는 건드리지 않는다
2. **단위 eval 을 주력으로** — ②③④ 를 얼린 입력에 대해 노드 단위로 돌리면 표본당 콜이
   1개로 줄어 **같은 쿼터로 표본을 4~10배** 가져갈 수 있다. E2E 는 확인용으로 소규모만
3. **표본 조정** — arm B 만 페르소나 30 × seed 1 로 시작하고, 쿼터가 남으면 seed 를 늘린다.
   arm A(400 RPM)·C 는 전량 수행
4. **지연 지표 분리** — 스로틀이 걸린 실행의 지연은 무의미하다. **p50/p95 는 각 arm 10건씩
   스로틀 없이 따로 측정**하고, 품질 지표 실행분과 섞지 않는다

> arm B 의 예상 소요: 직렬화 + 4초 간격 기준 약 40~50분/세션, 하루 한도로 1세션.
> **arm B 만 여러 날에 걸친다**는 전제로 일정을 잡는다.

## 5. LLM-as-judge 규율

- 순서 무작위화 + **A/B 스왑 후 양쪽 판정이 일치할 때만 채택** (position bias)
- judge 는 **피평가 3사와 무관한 모델** (self-preference bias). 3사 교차 judge 로
  편향 크기를 실측해 부록에 싣는다
- 근거를 먼저 쓰게 하고, tie 를 허용한다
- rubric 은 문서에 원문 그대로 싣는다

## 8. 계측 도구 — 랭스미스를 쓸까

**주력은 로컬 JSON 하네스, LangSmith 는 트레이싱만 선택적으로.**

- 쓸 만한 점: LangGraph 앱이라 환경변수만으로 **노드별 지연·토큰이 자동 수집**된다.
  직접 콜백을 짜는 수고가 사라지고, 트레이스 화면을 리포트에 붙일 수 있다
- 안 쓰는 이유: 핵심 지표가 전부 도메인 특화(200m 스톱쌍, 대분류 다양성, 화이트리스트
  이탈, 스케줄 정합성)라 **내장 evaluator 로는 하나도 안 되고 결국 직접 짜야 한다.**
  또 결과가 SaaS 에 있으면 이 저장소에 커밋되는 재현 가능한 산출물이 남지 않는다
- 결론: 결과 JSON 은 저장소에 남기고, 지연 분해가 필요할 때만 트레이싱을 켠다
