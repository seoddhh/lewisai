# 코스 생성 LLM 모델 비교 평가 설계

> 작성일 2026-08-04 · **측정 완료.** 1~9절은 실행 전에 정한 설계이고, 10절이 실제 측정 결과입니다.
> 설계와 다르게 실행된 부분은 해당 절에 표시했습니다.
>
> 이 문서는 `docs/llm-provider-eval.md`(3개 모델 비교 계획)를 대체합니다.

## 1. 무엇을 왜 비교하는가

이 서비스는 사용자가 고른 조건으로 서울 하루 코스를 만들어 줍니다. 그 과정에서 LLM이 하는 일은 두 가지입니다. 하나는 검색으로 추려진 후보 장소 목록에서 실제로 갈 곳을 고르는 일이고, 다른 하나는 확정된 일정 위에 코스 제목과 선정 이유, 장소별 설명과 추천 행동을 쓰는 일입니다. **이 문서는 "어떤 모델을 써야 하는가"에 답하는 문서가 아닙니다.** **같은 프롬프트와 같은 LangGraph 구조 위에서 모델만 바꿨을 때 무엇이 어떻게 달라지는지를 관찰하고 기록하는 문서**입니다.

같은 파이프라인에 서로 다른 모델을 끼웠을 때 궁금한 것은 이런 것들입니다. 어떤 모델은 후보 목록 밖의 장소를 지어내고 어떤 모델은 안 지어내는가. 같은 한국어 프롬프트인데 토큰 사용량이 얼마나 다른가. 응답이 잘리거나 형식을 어기는 빈도가 다른가. 만들어 낸 코스의 서술 품질에 실제로 구분할 만한 차이가 있는가.

`solar-open2`를 기준으로 두는 이유는 **오늘자(26.08.04)기준으로 사용하고 있는 api로 비교 대상이 필요하기 때문**입니다.

## 2. 어떤 환경에서 진행하는가

### 2.1 고정하는 것

LLM모델을 제외하고 모든 조건을 아래와 같이 고정하였습니다.

| 고정 항목 | 값 | 왜 고정하는가 |
|---|---|---|
| 장소 데이터 | `data/embed/places.json` **1,651곳** | 후보로 나올 수 있는 장소가 같기 위하여 |
| 벡터 데이터베이스 | Chroma `seoulro_v2` 컬렉션, 1,651건, 4096차원 | 검색 결과가 같아야 합니다 |
| 임베딩 모델 | **`qwen3-embedding:8b`** (ollama, 로컬 실행) | 검색 품질은 이번 실험의 비교 대상이 아님 |
| 프롬프트 | 현재 코드에 있는 원문 그대로 | 모델별로 프롬프트를 손보면 모델 성능인지 프롬프트 튜닝 효과인지 알 수 없습니다 |
| 요청 세트 | 페르소나 15개 (3절) | 모든 모델이 완전히 같은 15개 요청을 처리합니다 |
| 샘플링 설정 | `LLM_TEMPERATURE=0.7`, `LLM_MAX_TOKENS=4000` | 모델별 기본값 차이를 없앱니다 |
| 코드 | 실험 시작 시점의 커밋 하나 | 중간에 코드가 바뀌면 앞뒤 수치를 이어 붙일 수 없습니다 |

**여기서 특히 중요한 것은 임베딩 모델을 고정한다는 점입니다.** 임베딩이 같으면 검색 단계가 만들어 내는 후보 장소 목록이 모든 모델에서 동일합니다. 따라서 이 실험이 측정하는 것은 검색 성능이 아니라, **똑같은 후보 목록을 받았을 때 모델이 얼마나 잘 고르고 얼마나 잘 쓰는가**를 평가합니다.

### 2.2 비교할 네 개 모델

| 구분 | 모델 | 설정 방법 | 역할 |
|---|---|---|---|
| 기준 | **`solar-open2`** | `LLM_PROVIDER=upstage`<br>`UPSTAGE_MODEL=solar-open2` | **현재 서비스가 쓰는 모델.** 나머지는 전부 이 모델과 비교합니다 |
| 후보 1 | **`solar-pro4`** | `LLM_PROVIDER=upstage`<br>`UPSTAGE_MODEL=solar-pro4` | 베타버전으로 정식 출시 전 무료 테스트 기간에 사용함. |
| 후보 2 | **`gemini-3.1-flash-lite`** | `LLM_PROVIDER=gemini`<br>`GEMINI_MODEL=gemini-3.1-flash-lite` | 일정 호출 무료 티어로 solar-open2 이전에 사용하던 모델|
| 후보 3 | **`claude-haiku-4-5`** | `LLM_PROVIDER=claude`<br>`CLAUDE_MODEL=claude-haiku-4-5` | 앤트로픽 경량 모델 |


**추론 기능이 있는 모델은 추론을 끄고 진행하였습니다.** 추론 과정에서 나오는 토큰이 출력 한도를 먼저 소진해 버리면 실제 답변이 중간에 잘리고, 그러면 JSON 파싱이 실패해서 코스가 아예 안 만들어집니다. 
모든 모델에 `LLM_REASONING_EFFORT=none`을 적용하였습니다.

## 3. 어떤 요청으로 테스트하는가 — 페르소나 15개

### 3.1 설계 원칙

페르소나는 서비스를 실제로 쓸 법한 사용자 한 명의 조건 묶음입니다. 15개를 만들되, 개수보다 **어떤 경로를 덮는지가 훨씬 중요합니다.** 조건이 한쪽으로 쏠리면 그 조건에서만 유리한 모델이 이기기 때문입니다.

코스 생성 코드에는 조건에 따라 동작이 갈리는 지점이 여러 곳 있습니다. 15개 안에서 이 갈래를 모두 지나가도록 배분합니다.

| 축 | 값 | 배분 원칙 |
|---|---|---|
| 사용자 유형 | 현지인 / 여행자 | 대략 절반씩 나눕니다. 두 유형은 기본 시간대와 권역 배분 방식이 다릅니다 |
| 일수 | 1일 / 2일 / 3일 | 여러 날 요청을 최소 5개 넣습니다. 이때만 일차별 병렬 호출 경로를 지나갑니다 |
| 권역 | 9개 권역 | 데이터가 많은 권역(종로·중구)과 **적은 권역(관악·사당, 잠실·송파)을 반드시 함께** 넣습니다. 후보가 부족할 때의 동작이 갈립니다 |
| 목적 | 7종 | 전체의 59%에 붙어 있는 `데이트`와, 장소 수가 적은 `체험·놀거리`를 섞습니다 |
| 동반자 | 연인·친구·가족·아이·부모님·혼자 | 최소 4종. 개인화 가중치가 실제로 작동하는지 보려면 필요합니다 |
| 시간대·식사 | 선택 / 미선택 | **시간대를 안 고른 현지인 요청**을 최소 1개 넣습니다. 시간표 없이 장소만 나오는 경로입니다 |
| 입력 방식 | 조건 선택 / 자연어 | 자연어 요청을 3개 정도 넣습니다. 자연어를 조건으로 바꾸는 단계를 평가하려면 필요합니다 |
| 자유 입력 | 없음 / 있음 / **불가능한 요구** | "위치는 종로인데 한강에서 자전거" 같이 조건상 들어줄 수 없는 요구를 2개 넣습니다 |

### 3.3 반복 실행

같은 페르소나를 **`seed` 값을 바꿔 3회씩** 돌립니다. 이 서비스는 같은 조건이면 같은 코스를 내도록 만들어져 있고, `seed`를 주면 다른 코스가 나옵니다. 세 엔드포인트 모두 이 값을 받습니다.

반복이 필요한 이유는 표본을 늘리기 위해서가 아니라 **한 번 실행의 우연을 걸러내기 위해서**입니다. 같은 모델을 같은 조건으로 세 번 돌렸을 때의 결과 차이보다 모델 간 차이가 작다면, 그 차이는 모델 때문이라고 말할 수 없습니다.

```
페르소나 15개 × 모델 4개 × seed 3회 = 총 180회 실행
```

## 4. 어떻게 진행하는가

### 4.1 모델을 한 번에 하나씩 순차로 돌립니다

코드에서 모델 설정은 프로세스가 시작할 때 한 번만 읽히고 그대로 고정됩니다. 따라서 한 프로세스 안에서 모델을 바꿔 가며 돌릴 수 없고, 모델마다 프로세스를 따로 띄워야 합니다.

프로세스를 여러 개 동시에 띄우는 것 자체는 가능합니다. 그러나 **그렇게 하면 속도 측정값을 쓸 수 없게 됩니다.** 모든 프로세스가 같은 임베딩 서버(로컬 ollama) 하나를 함께 쓰기 때문에 서로 순서를 기다리게 되고, 그 대기 시간이 검색 단계 소요 시간에 섞여 들어갑니다.


### 4.2 제미나이는 호출 간격을 강제합니다

제미나이 무료 사용 한도는 **분당 15회 · 분당 25만 토큰 · 하루 500회**입니다.
코스를 만들 때 마지막 글쓰기 단계에서 여러 요청을 한꺼번에 보내기 때문에, 그냥 돌리면
코스 한 건만으로도 순간 한도를 넘깁니다.

실측한 호출량을 세 한도에 각각 대보면 이렇습니다.

| 한도 | 필요량 | 판정 |
|---|---|---|
| 하루 500회 | 292회 (58%) | 여유 있음. 재시도분 208회 남음 |
| 분당 25만 토큰 | 약 2~3만 토큰 | 여유 있음. 제약이 아님 |
| **분당 15회** | — | **여기가 유일한 병목** |

그래서 **평가 도구 쪽에서 LLM 호출 사이에 4.5초 간격을 강제**했습니다.
분당 13.3회로 한도에 15% 여유를 둔 값입니다. 서비스 코드는 건드리지 않았습니다.

**결과: 45회 전부 성공, 호출 한도 오류 0건, 총 23분.** 
다만 이 방식 때문에 **제미나이의 소요 시간은 다른 모델과 비교할 수 없습니다.**
측정된 시간의 대부분이 강제 대기 시간이기 때문입니다. 10-1 표에서 해당 칸을
"비교 불가"로 표시한 이유입니다.

### 4.3 실행할 때 지킬 것

| 항목 | 내용 |
|---|---|
| 임베딩 서버 예열 | 모델마다 실행 시작 전에 임베딩을 한 번 미리 호출합니다. 처음 호출은 모델을 메모리에 올리느라 약 2.8초가 걸리고 그 다음부터는 0.15초라, 예열하지 않으면 검색 단계 시간이 왜곡됩니다 |
| 실행 시각 기록 | 혼잡도와 문화행사 정보는 시간에 따라 바뀌고, 이 정보가 글쓰기 단계의 입력으로 들어갑니다. 모델별 실행 간격이 벌어질수록 입력이 달라지므로, 가능한 짧은 기간 안에 몰아서 돌리고 실행 시각을 남깁니다 |
| 결과 저장 | 모든 실행 결과를 JSON 파일로 저장합니다. 채점과 심사는 저장된 파일을 읽어서 나중에 수행합니다 |

### 4.4 심사는 생성이 다 끝난 뒤에 별도로 진행합니다

심사 모델은 **코스를 만드는 동안 같이 돌리지 않습니다.** 네 모델의 결과가 전부 저장된 다음에 그 파일들을 읽어서 판정합니다. 이렇게 나누는 이유는 세 가지입니다.

첫째, 두 모델의 결과를 나란히 놓고 비교하려면 양쪽이 다 만들어져 있어야 합니다. 모델을 순차로 돌리는 이상 애초에 동시 진행이 불가능합니다.

둘째, 심사 기준을 고치거나 심사 모델을 바꾸고 싶을 때 **코스 생성을 다시 하지 않아도 됩니다.** 비용과 시간이 드는 쪽은 코스 생성이지 심사가 아닙니다.

셋째, 어느 모델이 만든 결과인지 감춘 채로 심사해야 하는데, 저장된 파일에서 모델 이름을 떼고 순서를 섞는 편이 훨씬 간단합니다.

## 5. 무엇을 어떻게 평가하는가

평가 항목을 다섯 갈래로 나눕니다. **이 중 앞의 세 갈래는 코드로 계산하고, 네 번째만 심사 모델을 씁니다.** 심사 모델을 쓰는 범위를 좁게 잡는 것이 이 평가 설계의 핵심입니다. 전부 모델 판정에 맡기면 "결국 AI가 AI를 채점한 것"이라는 한마디로 결과 전체가 흔들리기 때문입니다.

### 5.1 운영 지표 — 실행 기록만으로 계산

서비스를 운영할 수 있느냐를 봅니다. 품질과 무관하게 여기서 걸리면 채택할 수 없습니다.

| 항목 | 의미 | 계산 방법 | 좋은 방향 |

| JSON 파싱 실패율 | 응답이 형식에 안 맞아 부분 복구가 작동한 비율 | 복구 함수 호출 횟수 | 낮을수록 |
| 응답 잘림 비율 | 출력 한도에 걸려 답변이 중간에 끊긴 비율 | API 응답의 종료 사유 | 낮을수록 |
| 코스 1건 소요 시간 | 요청부터 완성까지 | 중앙값과 90번째 값 | 낮을수록 |
| 단계별 소요 시간 | 장소 선정 / 글쓰기 각각 | 글쓰기는 여러 요청을 동시에 보내므로 **평균이 아니라 가장 느린 요청 기준** | 낮을수록 |

### 5.2 규칙 준수 — 정답 없이 코드로 채점

**이 갈래가 이번 평가에서 가장 신뢰할 만한 근거입니다.** 정답지가 필요 없고, 사람이나 모델의 주관이 개입할 여지도 없습니다. 요청 조건과 결과를 대조하기만 하면 되기 때문입니다.

| 항목 | 의미 | 좋은 방향 |
|---|---|---|
| **없는 장소를 지어낸 비율** | 후보 목록에 없는 장소 이름이 결과에 등장한 비율 | **0** (아니면 탈락) |
| 권역 준수율 | 요청한 권역 안에 있는 장소의 비율 | 높을수록 |
| 목적 준수율 | 요청한 목적 태그를 가진 장소의 비율 | 높을수록 |
| 장소 수 준수율 | 하루에 넣어야 할 장소 수를 맞춘 비율 | 높을수록 |
| 일수 구조 준수율 | 요청한 일수만큼 일정이 나뉘었는지 | 높을수록 |
| 장소 중복률 | 한 코스 안에 같은 장소가 두 번 나온 비율 | 낮을수록 |
| 항목 누락률 | 선정 이유, 할 일, 체류시간이 비어 있는 비율 | 낮을수록 |
| 동선 밀집도 | 이어지는 장소 사이 거리의 중앙값 | 낮을수록 |
| 종류 다양성 | 코스 하나에 들어간 서로 다른 장소 종류의 수 | 높을수록 |
| 일정 정합성 위반 | 영업시간 밖에 배치했거나 이동시간을 초과한 건수 | 낮을수록 |

**없는 장소를 지어내는 문제는 다른 어떤 항목보다 중요합니다.** 이 서비스는 후보 목록을 프롬프트에 넣어 주고 그 안에서만 고르라고 지시합니다. 그런데도 목록 밖 이름이 나온다면 사용자가 존재하지 않는 장소로 찾아가게 됩니다. 따라서 이 항목은 점수가 아니라 **통과·탈락 기준**으로 다룹니다.

이 갈래의 지표는 이미 만들어 둔 `scripts/profile_diversity.py`가 재는 항목과 겹칩니다. 새로 만들지 않고 그대로 씁니다. 기존 계측과 숫자가 이어져야 비교가 되기 때문입니다.

### 5.3 자료 근거 — 지어낸 설명을 잡아냅니다

검색으로 가져온 자료에 실제로 있는 내용만 가지고 설명을 썼는지 봅니다. 코스 생성에서 가장 위험한 오류는 그럴듯하지만 사실이 아닌 문장입니다.

| 항목 | 의미 | 채점 방법 | 좋은 방향 |
|---|---|---|---|
| 근거 있는 서술 비율 | 장소 설명의 내용이 그 장소의 원본 자료에서 확인되는가 | 심사 모델 | 높을수록 |
| 근거 없는 주장 비율 | 원본 자료에 없는 시설·고유명사를 언급한 비율 | 규칙 + 심사 모델 | 낮을수록 |
| 자료 활용률 | 프롬프트에 넣어 준 장소 특징 중 실제로 설명에 반영된 비율 | 코드 | 높을수록 |
| 없는 가게 지어내기 | 실재하지 않는 상호나 시설을 만들어 낸 건수 | 심사 모델 | 0 지향 |

### 5.4 글 품질 — 여기서만 심사 모델을 씁니다

| 항목 | 의미 | 채점 방법 | 좋은 방향 |
|---|---|---|---|
| 상투어 밀도 | "다채로운", "다양한", "아름다운" 같은 광고성 표현의 출현 빈도 | **코드** | 낮을수록 |
| 구체어 밀도 | 실제 시설명과 행동 동사의 비율 | **코드** | 높을수록 |
| 지시사항 위반 | 프롬프트에서 금지한 표현(방문 시각 언급 등)을 쓴 건수 | 코드 + 심사 모델 | 낮을수록 |
| **1:1 비교 선호도** | 두 모델의 결과를 나란히 놓고 어느 쪽이 나은지 | 심사 모델 | 높을수록 |

상투어와 구체어 밀도는 단어를 세기만 하면 되므로 **심사 모델보다 신뢰도가 높습니다.** 만약 심사 모델의 판정과 이 단어 통계가 어긋난다면 단어 통계를 믿고, 그 사실을 결과에 함께 적습니다.

### 5.5 사람 확인 — 심사 모델을 검증합니다

심사 모델의 판정을 그대로 믿을 수는 없습니다. 심사 모델도 결국 LLM이기 때문입니다. 그래서 **심사 결과를 쓰기 전에 심사 모델이 믿을 만한지부터 확인합니다.**

방법은 이렇습니다. 심사가 끝난 결과 중 20건 정도를 무작위로 뽑아, 어느 모델 것인지 모르는 상태로 직접 읽고 판정합니다. 그 다음 사람 판정과 심사 모델 판정이 얼마나 일치하는지를 계산합니다. 일치율이 낮게 나온 항목은 **결론에서 제외합니다.**

## 6. 심사 모델은 무엇을 쓰는가

### 6.1 gpt-oss-120b (NVIDIA NIM api 호출)

심사 모델은 **비교 대상 네 개와 아무 관계가 없는 회사의 모델**이어야 합니다. 모델은 자기 회사 모델의 문체를 더 좋게 평가하는 경향이 있어서, 비교 대상 중 하나를 심사에 쓰면 그 회사가 유리해집니다.

비교 대상 네 개가 업스테이지·구글·앤스로픽 세 회사를 이미 덮고 있으므로, 네 번째 회사의 모델이 필요합니다. **OpenAI의 공개 가중치 모델 `gpt-oss-120b`를 NVIDIA NIM API로 호출해 쓰기로 합니다.**

| 항목 | 내용 |
|---|---|
| 모델 | `openai/gpt-oss-120b` |
| 호출 경로 | NVIDIA NIM API — OpenAI 호환 형식 |
| 비교 대상과의 관계 | 없음 (업스테이지·구글·앤스로픽 어디에도 속하지 않습니다) |
| 판정 1회 소요 | 약 2초 |
| 예상 호출 수 | 페르소나 15 × seed 3 × 3쌍 × 순서 바꿔 2회 = **270회** |
| 예상 총 소요 | 약 10분 |
| 사용 조건 | NVIDIA API 무료 사용 약관은 **테스트와 평가 목적**을 허용합니다. 이 평가 도구가 정확히 그 용도에 해당합니다 |

### 6.1 1:1 비교 방식

네 모델을 모두 짝지으면 6쌍이 나옵니다. 그러나 이 평가가 답해야 할 질문은 "**지금 쓰는 모델을 바꿀 이유가 있는가**"입니다. 그래서 **기준 모델과 나머지 셋을 각각 비교하는 3쌍**으로 진행합니다.

```
solar-open2  vs  solar-pro4
solar-open2  vs  gemini-3.5-flash-lite
solar-open2  vs  claude-haiku-4-5
```

상위 두 모델이 접전이면 그때 그 둘만 추가로 붙입니다.

### 6.2 판정이 흔들리지 않게 하는 장치

심사 모델은 여러 이유로 한쪽에 치우칠 수 있습니다. 각각에 대응책을 둡니다.

| 치우침 | 대응 |
|---|---|
| **먼저 보여준 쪽을 고르는 경향** | 순서를 무작위로 섞고, **A와 B의 위치를 바꿔 두 번 판정한 뒤 두 판정이 일치할 때만 결과로 인정합니다.** 엇갈리면 무승부 처리합니다 |
| **자기 회사 모델을 선호하는 경향** | 비교 대상과 무관한 회사의 모델을 씁니다. 추가로 비교 대상 중 하나로도 같은 표본을 판정해 보고, 두 심사 결과의 차이를 편향 크기로 기록합니다 |
| **긴 글을 좋게 보는 경향** | 글 길이를 점수와 분리해서 따로 기록합니다 |
| 판정이 매번 달라지는 문제 | 심사 모델의 온도를 0으로 두고, 점수보다 판단 근거를 먼저 쓰게 합니다. 무승부를 허용합니다 |

판정 기준 문서는 **줄여 쓰지 않고 원문 그대로** 이 문서 부록에 싣습니다. 기준을 감추면 결과를 검증할 수 없습니다.

또한 총점 하나로 합치지 않고 **세 축을 따로 매깁니다.**

| 축 | 보는 것 |
|---|---|
| 실행 가능성 | 이 코스를 실제로 그대로 다닐 수 있는가 |
| 조건 반영도 | 사용자가 고른 조건이 결과에 실제로 반영됐는가 |
| 한국어 자연스러움 | 읽었을 때 어색하지 않은가 |

축마다 이기는 모델이 다를 수 있고, 그 사실 자체가 결정에 필요한 정보입니다.

| 코스 1건당 비용 | 기준 모델 대비 **3배 이내** | 감점 | 품질이 확실히 낫다면 비용을 더 낼 수 있지만, 배수가 커지면 트래픽이 늘 때 감당이 안 됩니다 |
| 1:1 비교 선호도 | **60% 이상**이어야 교체를 검토 | 미만이면 **바꿀 이유 없음** | 아래 단서를 함께 봅니다 |
| 사람 판정과의 일치도 | **0.4 이상** | 해당 항목을 결론에서 제외 | 이 값 아래면 심사 모델이 사람과 다른 기준으로 보고 있다는 뜻입니다 |

### 7.3 1:1 비교 선호도를 해석하는 방법

이 항목만 단서가 붙습니다. 8절에서 설명하듯 **표본 15개로 통계적으로 확인할 수 있는 것은 승률 80% 이상뿐**입니다. 그래서 결과를 세 구간으로 나눠 다르게 다룹니다.

| 승률 | 해석 | 결정 |
|---|---|---|
| **80% 이상** (15번 중 12번 이상) | 우연으로 설명되지 않습니다 | **품질을 근거로 교체를 결정할 수 있습니다** |
| **60~80%** | 나아 보이지만 우연일 가능성을 배제할 수 없습니다 | 품질만으로 결정하지 않고, **속도·비용·안정성으로 판단합니다** |
| **60% 미만** | 차이를 확인할 수 없습니다 | **바꿀 이유가 없습니다** |

즉 60%는 "이 아래면 볼 것도 없다"는 하한선이고, 80%는 "품질만으로 결론을 낼 수 있다"는 상한선입니다. 그 사이 구간에서는 품질 점수를 결정 근거로 쓰지 않습니다.

## 8. 결과를 어떻게 해석할 것인가

### 8.1 표본 15개로 말할 수 있는 것과 없는 것

페르소나를 15개로 잡았습니다. 이 규모로 어디까지 주장할 수 있는지 미리 정리해 둡니다.

| 평가 갈래 | 15개로 충분한가 | 이유 |
|---|---|---|
| 규칙 준수 (5.2) | **충분합니다** | 코스 단위가 아니라 **장소 단위로 셉니다.** 15개 요청에서 나오는 장소는 seed 3회를 합쳐 약 360곳이므로 비율을 재기에 충분합니다 |
| 운영 지표 중 비용·호출 수·실패율 | 충분합니다 | 실행마다 값이 나오므로 15회로도 안정적입니다 |
| 운영 지표 중 소요 시간 상위값 | 부족합니다 | 90번째·95번째 값은 표본이 더 필요합니다. **중앙값과 최댓값으로 보고합니다** |
| 1:1 비교 선호도 (5.4) | **큰 차이만 잡힙니다** | 아래 참고 |

1:1 비교는 15번 대결에서 몇 번 이겼는지를 세는 방식입니다. 이때 우연으로 설명되지 않으려면 **15번 중 12번 이상, 즉 승률 80%가 나와야 합니다.** 11번(73%)이면 우연히 그럴 확률이 12%나 되므로 차이가 있다고 말할 수 없습니다.

따라서 **"어느 모델이 60~70% 정도 낫다"는 결론은 이 표본으로 낼 수 없습니다.** 압도적인 차이만 확인할 수 있습니다.

### 8.2 그래서 결론을 이렇게 씁니다

- 차이를 확인하지 못했을 때: ~~"두 모델은 차이가 없다"~~ → **"15개 표본에서는 유의한 차이를 확인하지 못했다"**
- 없는 장소 지어내기가 0건일 때: ~~"환각률 0%"~~ → **"약 360개 장소에서 1건도 나오지 않았다 (비율로는 1% 미만)"**

합격·탈락 기준은 통계적 검정이 아니라 최소 요건이므로 15개 표본에서도 그대로 적용합니다.

### 8.3 반복 실행 결과를 반드시 함께 싣습니다

같은 모델을 같은 조건으로 3번 돌렸을 때의 편차를 모든 지표에 함께 적습니다. **모델 간 차이가 이 편차보다 작으면 순위를 주장하지 않습니다.**

## 10-7. 관찰된 차이 요약

이 실험에서 실제로 확인된 것만 적습니다.

**모델을 바꿔도 달라지지 않은 것**

- 후보 목록 밖 장소를 지어내는 일은 네 모델 모두 0건이었습니다.
- 장소 중복, 응답 잘림도 네 모델 모두 0건이었습니다.
- 시드에 따른 결과 흔들림 폭(31~41%)이 비슷했습니다.
- 코스 서술의 품질은 심사 모델이 구분하지 못했습니다.

**모델을 바꾸면 달라진 것**

- **토큰 사용량**이 가장 크게 갈렸습니다. 같은 한국어 프롬프트에 대해 클로드가 기준 모델의
  1.88배를 씁니다. 이건 성능이 아니라 토크나이저의 차이이며, 비용에 직결됩니다.
- **소요 시간의 최댓값**이 갈렸습니다. 클로드가 17.0초로 가장 안정적이었고 `solar-pro4`가
  47.3초로 가장 나빴습니다. 중앙값보다 최댓값의 차이가 훨씬 컸습니다.
- **생성 실패율**이 0.0~4.4%로 갈렸습니다. 다만 표본 45회 기준이라 1~2건 차이이므로
  이 순위를 단정할 수는 없습니다.

**이 파이프라인에서 모델이 바꿀 수 있는 여지가 좁다는 점**

품질 차이가 관찰되지 않은 것은 설계와 무관하지 않습니다. 이 파이프라인에서 LLM이 하는 일은
**이미 좁혀진 후보 목록에서 고르고, 이미 확정된 시간표 위에 문구를 얹는 것**입니다.
장소 후보는 검색과 재랭킹이 정하고, 방문 순서와 시각은 순수 계산이 정합니다.
모델이 개입할 수 있는 범위 자체가 좁게 설계되어 있어서, 모델을 바꿔도 결과가 크게
달라지지 않습니다. 이는 의도한 설계의 결과이기도 합니다.

**표본 15개로 확인할 수 있었던 것과 없었던 것**

| 항목 | 결론을 낼 수 있는가 |
|---|---|
| 없는 장소 지어내기 | **가능** — 1,098곳 전수 검사, 0건 |
| 토큰 사용량 | **가능** — 차이가 배수 단위로 명확 |
| 소요 시간 | **가능** (제미나이 제외) |
| 생성 실패율 | 불가 — 1~2건 차이라 순위를 단정할 수 없음 |
| 서술 품질 | **불가** — 무승부가 많고 순서 뒤집힘이 40~60% |

## 11. 평가의 한계

**첫째, 평가 환경과 실제 배포 환경이 다릅니다.** 이 평가는 로컬에서 돌리는 `qwen3-embedding:8b`로 검색합니다. 그런데 배포 환경에서는 이 크기의 임베딩 모델을 그대로 올리기 어려울 수 있고(서빙시 비용문제), 다른 임베딩으로 바꾸면 검색 결과가 달라져 후보 장소 목록이 바뀝니다. **가장 좋은 임베딩 모델기준 모델의 응답을 확인하기 위함 eval용 문서입니다**

**둘째, 표본이 15개입니다.** api 사용량 한계로 15개씩 3시드를 돌려 45가지의 비교밖에 하지 못하였습니다.


**셋째, 심사 모델도 결국 LLM입니다.** 이번 측정에서는 Human Evaluation은 진행하지 않았습니다. 사람 판정과의 일치도를 함께 싣지 않은 심사 점수는 근거로 쓰지 않습니다.  다만 심사 결과의 순서 뒤집힘이 40~60%로 나와 판정 자체가 무의미한 수준이었으므로, 사람 확인을 했더라도 결론은 달라지지 않았을 것으로 생각합니다.

**넷째, 프롬프트는 현재 사용하는 양식 그대로 씁니다.** 이 프롬프트는 지금 쓰는 모델에 맞춰 다듬어 온 것이라 기준 모델에 유리할 수 있습니다. 따라서 이 평가는 "**현재 프롬프트에서 각 모델이 어떻게 동작하는가**"를 보는 것이지 모델의 절대 성능을 재는 것이 아닙니다.
